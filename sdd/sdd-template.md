## 1. Введение {#1-introduction}

### 1.1 Назначение документа {#11-document-purpose}

Настоящий документ (Software Design Description, SDD) описывает архитектуру, структуру компонентов и дизайн веб-приложения «Puff & Plate». Документ предназначен для команды разработчиков, которая будет реализовывать систему, а также для сопровождающего персонала. 

Документ опирается на ранее согласованную спецификацию требований (SRS), где описано, *что* должна делать система, а SDD отвечает на вопрос, *как* она будет устроена технически.

### 1.2 Область применения {#12-subject-scope}

Веб-приложение «Puff & Plate» (Версия 1.0) предназначено для заказа еды на мероприятия (кейтеринг). 

Ключевые возможности системы включают: просмотр каталога сетов и блюд, конструктор заказа (корзина), автоматический расчет стоимости с учетом бесплатной доставки, оформление заказа и личный кабинет.

В область применения данного SDD входит описание клиент-серверной архитектуры, структуры базы данных и используемых технологий.

### 1.3 Определения, акронимы и сокращения {#13-definitions-acronyms-and-abbreviations}

## 2. Обзор дизайна {#2-design-overview}

### 2.1 Задачи стейкхолдеров {#21-stakeholder-concerns}

* **Разработчики:** Заинтересованы в понятной модульной структуре, четком разделении слоев (Frontend/Backend) и удобстве сопровождения кода.
* **Заказчик:** Заинтересован в том, чтобы архитектура обеспечивала выполнение функциональных требований (создание заказов, расчет доставки) и была экономически эффективной.
* **Конечные пользователи (Клиенты):** Заинтересованы в высокой скорости работы приложения (быстрая загрузка страниц) и надежности (сохранность данных о заказах).

### 2.2 Выбранные точки зрения {#22-selected-viewpoints}

#### 2.2.1 Контекст {#221-context}
**Адресует:** границы системы и внешние зависимости.
Система «Puff & Plate» взаимодействует со следующими внешними сущностями:
* **Пользователь:** взаимодействует через браузер (ввод данных, просмотр).
* **Внешние API:** В текущей версии внешние интеграции отсутствуют (кроме стандартных библиотек).

#### 2.2.2 Композиция {#222-composition}
**Адресует:** разделение ответственности и модульность.
Система разделена на три основных компонента:
1. **Frontend (SPA на React):** отвечает за пользовательский интерфейс.
2. **Backend (REST API на Spring Boot):** содержит бизнес-логику, включая расчет стоимости и бесплатной доставки.
3. **База данных (PostgreSQL):** отвечает за хранение и целостность данных.

#### 2.2.3 Логическое представление {#223-logical}
**Адресует:** статическую структуру дизайна и абстракции.
На бэкенде используется паттерн MVC (Model-View-Controller). Основные классы абстракций: сущности `Entity` (User, Dish, Set, Order), сервисы `Service` (обработка бизнес-логики) и контроллеры `Controller` (прием HTTP-запросов). На фронтенде используются функциональные React-компоненты.

#### 2.2.4 Физическое представление {#224-physical}
**Адресует:** физическую топологию и ограничения.
На этапе MVP физическая инфраструктура представлена одним виртуальным сервером (VPS), на котором развернуты Docker-контейнеры.

#### 2.2.5 Структура {#225-structure}
**Адресует:** внутреннюю организацию компонентов.
Бэкенд-приложение организовано в виде пакетов: `controller`, `service`, `repository`, `entity`. Это обеспечивает слабую связанность (low coupling) и высокую связность (high cohesion) внутри каждого слоя.

#### 2.2.6 Зависимости {#226-dependency}
**Адресует:** потребности в интеграции и приоритизацию.
Frontend зависит от Backend (через REST API). Backend зависит от Базы данных (через Hibernate/JPA). Направление зависимостей строго контролируется: контроллеры вызывают сервисы, сервисы вызывают репозитории.

#### 2.2.7 Информация {#227-information}
**Адресует:** структуру данных и их связи.
Основные сущности базы данных: `Users` (пользователи с телефоном), `Dishes` (блюда с ингредиентами), `CateringSets` (сеты), `Orders` (заказы), `OrderItems` (позиции заказа). Связи реализованы через внешние ключи.

#### 2.2.8 Интерфейс {#228-interface}
**Адресует:** взаимодействие через контракты.
Основным интерфейсом является REST API (JSON), через который Frontend получает данные от Backend.

#### 2.2.9 Взаимодействие {#229-interaction}
**Адресует:** последовательность сообщений в рантайме.
Типовой сценарий: Пользователь добавляет блюдо в корзину -> React отправляет POST-запрос на Backend -> Сервис пересчитывает стоимость (с учетом порога доставки) -> Возвращает обновленную корзину -> Frontend обновляет UI.

#### 2.2.10 Алгоритм {#2210-algorithm}
**Адресует:** логику обработки операций.
Ключевой алгоритм — расчет стоимости заказа:
1. Суммируется стоимость всех блюд и сетов.
2. Если сумма >= 200 BYN, доставка = 0.
3. Иначе доставка = 15 BYN.
4. Итог = сумма + доставка.

#### 2.2.11 Динамика состояний {#2211-state-dynamics}
**Адресует:** эволюцию состояний системы.
Состояния заказа: «Новый», «Подтвержден», «Готовится», «Доставлен», «Отменен».

#### 2.2.12 Параллелизм {#2212-concurrency}
**Адресует:** синхронизацию и потоки.
На уровне архитектуры используется многопоточность Spring Boot.

#### 2.2.13 Паттерны {#2213-patterns}
**Адресует:** повторно используемые решения.
Применяются паттерны: **MVC**, **Repository**, **DTO**, **Компонентный подход** во фронтенде (React).

#### 2.2.14 Развёртывание {#2214-deployment}
**Адресует:** отображение компонентов на узлы.
Все компоненты развертываются в Docker-контейнерах: Nginx (Frontend), Spring Boot (Backend), PostgreSQL.

#### 2.2.15 Ресурсы {#2215-resources}
**Адресует:** использование ограниченных ресурсов.
Основным ограниченным ресурсом является оперативная память сервера.

## 3. Проектные представления {#3-design-views}

### 3.1 Представление: Схема базы данных
* **ID**: VIEW-001-DataModel
* **Title**: Логическая и физическая схема базы данных
* **Viewpoint**: Информация (раздел 2.2.7)
* **Representation**: 
  Основные сущности и их атрибуты:
  * **users** (id, email, password_hash, name, phone_number, role, created_at);
  * **dishes** (id, name, price, description, ingredients);
  * **catering_sets** (id, name, persons_count, price, ingredients);
  * **orders** (id, user_id, delivery_address, delivery_date, total_items_price, delivery_cost, total_price, status, created_at);
  * **order_items** (id, order_id, item_type, item_id, quantity).
* **More Information**: Реализует требования REQ-INT-003, REQ-FUNC-007. Схема создается через Hibernate.

### 3.2 Представление: Слои Backend (MVC)
* **ID**: VIEW-002-BackendLayers
* **Title**: Структура слоев серверной части
* **Viewpoint**: Композиция (раздел 2.2.2), Логическое представление (раздел 2.2.3)
* **Representation**: 
  1. **Controller:** классы с `@RestController` (OrderController, MenuController). Принимают HTTP-запросы.
  2. **Service:** классы с `@Service` (OrderService, CalculationService). Содержат бизнес-логику (расчет доставки).
  3. **Repository:** интерфейсы, наследуемые от `JpaRepository`. Доступ к БД.
  4. **Entity:** Java-классы, маппящиеся на таблицы БД.
* **More Information**: Реализует требования REQ-FUNC-001, REQ-FUNC-007. 

### 3.3 Представление: Компоненты Frontend
* **ID**: VIEW-003-FrontendComponents
* **Title**: Структура клиентской части (React)
* **Viewpoint**: Композиция (раздел 2.2.2), Структура (раздел 2.2.5)
* **Representation**: 
  * **pages/**: Экраны (DashboardPage, ConstructorPage, LoginPage).
  * **components/**: Переиспользуемые UI-элементы (SetCard, DishCard, Cart, Calculator).
  * **api/**: Модули для отправки запросов к Backend.

### 3.4 Представление: Логика расчета стоимости
* **ID**: VIEW-004-CalcLogic
* **Title**: Алгоритм расчета стоимости заказа
* **Viewpoint**: Алгоритм (раздел 2.2.10)
* **Representation**: 
  1. Система суммирует стоимость всех позиций в корзине (`total_items_price`).
  2. Система проверяет: если `total_items_price` >= 200 BYN, то `delivery_cost` = 0.
  3. Иначе `delivery_cost` = 15 BYN.
  4. Итоговая стоимость = `total_items_price` + `delivery_cost`.
* **More Information**: Реализует требование REQ-FUNC-007.

## 4. Решения {#4-decisions}

В данном разделе зафиксированы ключевые архитектурные решения. Подробные обоснования (ADR) хранятся в папке `adr/`.

### 4.1 Выбор СУБД PostgreSQL
* **ID**: DEC-001-Database
* **Context**: Необходимо надежно хранить связанные данные (заказы, блюда, пользователи). Требуется поддержка транзакций (ACID).
* **Outcome**: Выбрана **«PostgreSQL»** (см. ADR-0005).

### 4.2 Выбор бэкенд-фреймворка Spring Boot
* **ID**: DEC-002-Backend
* **Context**: Требуется создать надежное и безопасное REST API.
* **Outcome**: Выбран **«Java + Spring Boot»** (см. ADR-0001).

### 4.3 Выбор фронтенд-библиотеки React
* **ID**: DEC-003-Frontend
* **Context**: Необходим быстрый и интерактивный интерфейс (SPA).
* **Outcome**: Выбран **«React + Vite»** (см. ADR-0002).

### 4.4 Выбор механизма аутентификации
* **ID**: DEC-004-Auth
* **Context**: Требуется разграничение доступа к истории заказов.
* **Outcome**: Выбран **«JWT»** (см. ADR-0003).
